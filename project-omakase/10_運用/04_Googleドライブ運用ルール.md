## 0. 前提：どちらが正本か

**Google ドライブが正本（マスター）です。GitHubリポジトリはスナップショット（履歴の保管庫）です。**

二重管理は必ず破綻するので、役割を先に固定します。

| | Google ドライブ | GitHub リポジトリ |
| --- | --- | --- |
| 役割 | **日々の作業・編集・共有** | 節目のスナップショットと変更履歴 |
| 編集するか | **する** | しない（読むだけ） |
| 更新頻度 | 随時 | 月1回、または大きな方針変更時 |
| 参照する場面 | 毎週の運用すべて | 「3ヶ月前はどう書いていたか」を追うとき |

**迷ったらドライブを見る。** リポジトリを編集し始めた瞬間に、どちらが最新か分からなくなります。

## 2. 移行手順（初回・15分）

### 手順

1. **ドライブの変換設定は OFF のままにする**
   ドライブ → 設定（歯車）→「アップロードしたファイルを Google ドキュメント エディタ形式に変換する」の**チェックは外したまま**にしてください。
   本プロジェクトは **Word（.docx）と Excel（.xlsx）のまま運用する**方針なので、変換は不要です。

2. **`Project_OMAKASE_Drive.zip` を解凍**して、フォルダごとマイドライブにドラッグ＆ドロップ
   フォルダ構造はそのまま再現されます

3. **Excel を開いて数値が入っているか確認する**（下記3章）

4. **README をドライブのトップに固定**（右クリック →「ワークスペースに追加」またはスターを付ける）

## 3. Office形式のまま運用する（本プロジェクトの方針）

**文書は Word（.docx）、表計算は Excel（.xlsx）のままドライブに置き、それぞれ Word / Excel で編集します。** Google ドキュメント／スプレッドシートへの変換は行いません。

### なぜ変換しないか

- 変換すると **元のファイルと変換後のファイルの2つが存在し得る**（＝正本が曖昧になる）
- Excel の条件付き書式・入力規則・表示形式は、変換で一部失われることがある
- 使い慣れた Excel の機能をそのまま使える

### 編集方法

| 環境 | 方法 |
| --- | --- |
| **PC（推奨）** | **Google ドライブ for desktop** を入れる。ドライブがローカルフォルダとして見え、Excel で直接開いて上書き保存すればそのまま同期される |
| PC（アプリなし） | ドライブ上でファイルをダブルクリック → Excel で開く／ダウンロード編集して再アップロード（**版が分かれやすいので非推奨**） |
| **スマホ** | ドライブアプリからファイルをタップ → **Google スプレッドシートアプリが .xlsx のまま開いて編集できる**（Office編集モード）。保存すると .xlsx のまま更新される |

**スマホからの週次KPI入力は、変換しなくても可能です。** Google スプレッドシートアプリは .xlsx を直接編集できます。

### 開いたときに必ず確認すること

3つの Excel は作成環境の制約でキャッシュ値を保存していないため、**開いた時点で全数式が再計算される設定**にしてあります。初回に一度開いて、上書き保存してください。それ以降は通常のExcelファイルと同じです。

| ファイル | 確認箇所 | 期待値 |
| --- | --- | --- |
| 01_収支計画モデル | 年次サマリの「検算値」ブロックと上の表の標準列 | **一致すること**（不一致なら前提条件が編集されている） |
| 02_KPIダッシュボード | 週次実績に数値を入れて月次サマリを見る | 月次に反映される |
| 店舗データベース | ステータス列のプルダウン | 6択（候補／訪問済／検証済／掲載中／要再確認／除外）が出る |

## 4. 命名規則

**ドライブは検索が主な導線なので、フォルダを開かなくても見つかる名前を付けます。**

| 種別 | 規則 | 例 |
| --- | --- | --- |
| 定常文書 | `番号_名前`（現行のまま） | `01_事業計画書` |
| 週次レビュー | `週次_YYYYMMDD` | `週次_20261025` |
| 月次レビュー | `月次_YYYYMM` | `月次_202610` |
| 商品バージョン | `商品名_vX.Y_YYYYMM` | `TokyoAccessGuide_v1.0_202701` |
| 写真素材 | `YYYYMMDD_エリア_店名` | `20260912_新宿三丁目_焼鳥◯◯` |
| 競合リサーチ | `競合分析_YYYYMM` | `競合分析_202610` |

**日付は必ず `YYYYMMDD` の8桁。** `10/25` のような書き方をすると並び順が壊れ、後から探せなくなります。

**バージョンはファイル名に持たせる。** ドライブの版履歴だけに頼ると、購入者に配ったのがどの版か分からなくなります。商品ファイルだけは名前で管理してください。

## 5. 共有・権限設計

副業なので当面は自分だけですが、**最初から権限を分けておかないと、外注を入れる段階で全部見えてしまいます。**

| フォルダ | 既定の権限 | 外注を入れるとき |
| --- | --- | --- |
| `00_戦略` | 自分のみ | **共有しない**（事業判断・収支が入っている） |
| `10_運用` | 自分のみ | 該当マニュアルのみ「閲覧者」で個別共有 |
| `20_実行` | 自分のみ | 共有しない |
| `30_管理` | 自分のみ | **共有しない**（収支・KPI） |
| `40_資産/写真素材` | 自分のみ | 編集者（動画編集の外注先） |
| `50_アーカイブ` | 自分のみ | 共有しない |
| `90_商品` | 自分のみ | 編集者（英語ネイティブチェック担当） |

**「リンクを知っている全員」は絶対に使わない。** 特に `90_商品` は、販売前の商品が流出します。共有は必ずメールアドレス指定で行ってください。

**販売する商品ファイル自体はドライブから直接配布しない。** 販売はGumroad経由に統一します（ドライブ共有だと購入者以外に転送され放題になります）。

## 6. 週次の運用フロー（ドライブ前提）

| タイミング | 場所 | やること |
| --- | --- | --- |
| 取材直後（現地） | スマホ | 音声メモを録音 → ドライブの `40_資産` に保存 |
| 取材当日夜 | PC | AIで構造化（P-02）→ **店舗データベース**に追記 |
| 火・木夜 | PC | 編集。写真素材を `40_資産/写真素材/YYYYMMDD_...` に格納 |
| 通勤中など | **スマホ** | **KPIダッシュボードの週次実績に数値を入力**（ここがスマホ運用の最大の利点） |
| 日曜夜 | PC | 数値確認 → **タスク管理**を更新 → 週次レビューを `50_アーカイブ` に新規作成 |
| 月末 | PC | 月次サマリ確認、収支計画モデルの前提を実績で更新 |

**週次レビューは、前週のファイルをコピーして日付を変えて使う。** 毎回テンプレートから作ると項目が揺れます。

## 7. バックアップと、リポジトリへの反映

**ドライブは同期であってバックアップではありません。** 誤削除はそのまま同期されます。

| 頻度 | やること |
| --- | --- |
| 月1回 | 主要文書と3つのスプレッドシートを **`.md` / `.xlsx` でダウンロード**し、GitHubリポジトリの `project-omakase/` を更新してコミット |
| 四半期 | `90_商品` の販売中バージョンをローカルにも保管（**購入者に配った版は必ず手元に残す**） |
| 随時 | 大きな方針変更をしたら、その時点でリポジトリに反映（意思決定ログが残るため） |

**リポジトリに反映する意味は、バックアップ以上に「いつ何を変えたかが追える」ことにあります。** 3ヶ月後に「なぜこの数字にしたか」を再現できるのは、履歴があるからです。

ゴミ箱の保持期間（30日）を過ぎると復元できません。**削除は月次レビューのタイミングでまとめて行い、その場では削除しない**ようにしてください。

## 8. やってはいけないこと

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | **リポジトリ側のファイルを編集する** | どちらが最新か分からなくなる。編集はドライブのみ |
| 2 | 同じ文書のコピーを複数作る（`_最新` `_修正版` など） | ドライブは版履歴を持っているので不要。コピーは混乱の元 |
| 3 | 「リンクを知っている全員」で共有する | 未発売の商品と収支情報が流出する |
| 4 | 販売商品をドライブ共有で配布する | 転送され放題になる。販売はGumroad経由に統一 |
| 5 | 番号接頭辞を外す | 並び順が崩れ、フォルダの意図が消える |
| 6 | 日付を `10/25` 形式で書く | ソートが壊れて後から探せない |
| 7 | 写真素材を日付なしで放り込む | 半年後にどの店の写真か分からなくなる |

## 9. 自動化（将来）

現時点では手動運用で十分ですが、以下は自動化する価値があります。着手は**運用が3ヶ月続いてから**。手が固まる前に自動化すると、間違った手順を固定してしまいます。

| 対象 | 手段 | 効果 |
| --- | --- | --- |
| 週次レビューのファイル自動生成 | Google Apps Script（毎週日曜にテンプレを複製） | 作成の手間と項目の揺れが消える |
| KPI入力のリマインド | Google カレンダー＋通知 | 入力忘れを防ぐ |
| 店舗データベース → ガイド原稿の生成 | Apps Script でMarkdown書き出し | 商品制作の工数が大きく減る |
| Gumroad売上のスプレッドシート転記 | Zapier | 週次入力の項目が1つ減る |

**このうち最も投資対効果が高いのは3番目**（店舗DB→原稿の自動生成）です。商品改訂のたびに手作業で組み直すのは、四半期ごとの更新を続ける上で最大のボトルネックになります。
